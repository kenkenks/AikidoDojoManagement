# 審査管理 業務仕様整理（構想・実装前）

作成日：2026-10-19  
位置付け：これまでの対話で確認した構想の整理。既存ARCH-024原文との照合、詳細仕様の確定は未実施。

## 1. 目的と対象

- 審査管理の対象は、先生を含む**道場所属の全会員**。
- 先生も稽古に参加するときは会員であり、会員カードで出席登録する。先生用カードは管理業務の操作に使用する。
- 審査管理画面で全会員の級段位、受審資格、進捗、審査日程、対象者、結果、履歴を把握・管理する。
- 先生も出席リストに表示する。先生専用の会費タイプは別途用意するが、出席・審査判定には影響させない。

## 2. 審査資格の3指標

| 指標 | 定義 | 注意 |
|---|---|---|
| 稽古回数 | 出席した**稽古枠数** | 道場の判定に使用。課金枠数ではない |
| 稽古日数 | 稽古した**異なる日付の数** | 同日に複数枠参加しても1日 |
| 経過年数 | 級段位の所定の起算日からの期間 | 特に昇段基準で重要 |

例：午前中に2稽古枠へ出席した場合、稽古回数は2、稽古日数は1。回数払いの会費計算に使う課金枠数は1となる場合があるが、**課金枠数は審査管理に一切関与しない**。課金枠数は会費請求の領域に限定する。

合気会の公式審査基準は稽古日数を用いる。一方、道場では稽古回数（稽古枠数）も扱う。必要な指標の組合せは審査基準マスタと道場運用に従う。

## 3. 基本業務フロー

1. 先生が審査日程を把握・登録する。
2. 全会員の受審資格・進捗を表示し、審査が近い会員を先生が識別できるようにする。
3. **先生が**審査対象者を登録する。資格到達による自動申込・自動確定は行わない。
4. 審査を実施し、審査レコードを**保留状態**で管理する。
5. 審査結果の通知後、先生が合否と必要な正式日付を登録して保留を解除する。
6. 結果に応じて現在級段位・起算日・履歴・進捗を整合させる。
7. 審査費は既存の請求・入金機能と連携する。

## 4. 保留と稽古実績の扱い

- **保留専用Entityや保留稽古実績の複製は原則作らない。** 審査レコードを保留状態にし、出席実績は既存レコードを参照する。
- **級**：審査日以降の結果待ち期間の稽古実績は、合格なら新しい級、不合格なら従前の級に帰属するよう判定する。
- **段**：正式な允可日を起算点として扱う。級と同じ仮計上ルールを機械的に適用しない。
- 保留解除は単なる表示変更ではなく、結果・会員級段位・起算日・履歴の整合性を保つ業務処理。
- 出席実績そのものを書き換えず、審査記録と基準日から計算する方向を基本とする。

## 5. 画面構想

### 先生向け審査管理画面
- 全会員一覧（先生も含む）と検索。
- 現在級段位、次回審査級段位、稽古回数・稽古日数・経過年数、到達状況を表示。
- 審査日程、審査が近い会員、審査対象者、保留中の審査を確認。
- 審査対象者登録、結果通知に基づく合否登録・保留解除、履歴参照。

### 既存画面との関係
- 先生の出席リストにも審査接近・予定状況を表示できるようにする。
- 先生専用の出席登録画面は将来廃止する構想。ただし代理登録・訂正等の現行機能を確認するまで廃止は決定しない。
- 会員は既存の出席・進捗表示を利用する。

## 6. アーキテクチャと実装順序

- 当面は**審査管理画面の成立**を優先し、既存の進捗計算・級段位マスタ・審査基準マスタ・会員管理・請求管理を再利用する。
- ビジネスレイヤの審査管理ユニットを業務の窓口にする構想。
- 将来は判定の詳細を独立した**判定BOX／判定ファンネル**へ切り出し、業務側が判定内部を知らずに利用できるようにしたい。**これは希望する将来像であり、現状実装済みの構造ではない。**
- 判定ロジックを画面へ新たに埋め込まない。既存の `/api/webconnect` と DAO/DTO を優先して再利用し、新規API増殖を避ける。
- 結果確定時の複数データ整合性と重複確定防止は実装上の要確認事項。

## 7. 現状と不足（調査報告に基づく）

**既存**：級段位マスタ（Firestore `ranks` 37件）、審査基準マスタ（`examination_standards` 30件）、審査進捗表示、会員の現在級段位、GASの審査費追加請求、Firebaseの通常請求・入金機能。

**不足**：独立した審査日程・対象者・結果・履歴の管理、審査レコードの保留・確定処理、Firebase側の審査費追加請求Command、先生用審査管理画面。

## 8. 実装前に原資料・現場運用と照合する事項

- ARCH-024の原文、各級段位の回数・日数・年数の具体的条件と年齢条件。
- 級の審査日と段の正式允可日を使う具体的な起算日・保留解除条件。
- 審査日程の粒度、対象者登録の手順、審査結果通知の入力項目。
- 既存の級段位更新経路（出席登録・会員管理）と、審査結果確定との競合防止。
- 審査費請求の発生時点・重複防止・取消訂正、先生自身の結果を誰が確定できるか。
- 出席リストの表示方法と、先生用出席登録画面が現在担う代理登録・訂正機能。

---

**実装方針：** 画面を先に成立させる。ただし結果確定・履歴更新などの業務整合性は画面処理に押し込まず、既存業務層を活用して最小限の追加とする。
