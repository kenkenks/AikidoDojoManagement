# ARCH-018 Domain Decision Timing / 業務情報の確定タイミング

STATUS: ACTIVE
TYPE: ARCHITECTURE
AREA: COMMON
PRIORITY: HIGH

## 1. 目的

業務情報は「何を決めるか」だけでなく「現実世界のいつ決まるか」を設計対象とする。
デジタル化によって確定タイミングを移動すると、後続業務の前提を壊すためである。

## 2. 道場会費への適用

| 情報 | 正規確定タイミング | 保存・利用 |
|---|---|---|
| 会員 | 出席受付 | member_id |
| 月額／都度 | 出席登録 | 04_月次選択 |
| 回収予定額 | 出席・料金プラン確定後 | Billing / teacher reception view |
| 現金／PayPay | 支払い直前 | Payment |
| 回収実績 | 支払い後 | 06_入金ログ等 |

## 3. 冪等な補完処理

正規確定タイミングとは別に、安全網として同じ処理を後段から呼んでもよい。
ただし既存値と同一ならSKIP、矛盾する値ならエラーとし、無条件上書きしない。

道場会費では、会費回収側の月次選択処理を残してよい。出席時に既に同一planが登録済みなら冪等にSKIPする。

## 4. QR責務

QRは原則として識別子・受付コンテキストを運ぶ。
現場で後から決定・変更される業務状態をQRへ固定しない。

- member_id: QRでよい
- location_id: QRでよい
- teacher_id: QRでよい
- 月額／都度: 出席時に決めるためQRへ固定しない
- 現金／PayPay: 支払い直前に決めるためQRへ固定しない

## 5. 照合モデル

予定値は支払方法別に分けない。

```text
回収予定総額
   ↓
回収
   ├─ 現金実績
   └─ PayPay実績
   ↓
回収実績総額
   ↓
未回収額 = 回収予定総額 - 回収実績総額
```

## 6. 変更時ルール

業務情報の確定タイミングを変更する場合、次を上位から確認する。

`実運用 → Main Story → Story → ARCH → TASK → Runner → 実装 → E2E → ドメイン確認`

単体/E2EがPASSしていても、実運用順序と異なる場合は仕様不整合になり得る。
