# ARCH-019 View Summary Contract / 高速参照View契約

STATUS: ACTIVE
TYPE: ARCHITECTURE
AREA: COMMON
PRIORITY: HIGH

## 1. 目的

Viewは表示・参照の高速化のためのサマリー（Read Model）とする。
表示のたびに複数の正本シートを横断して情報収集・集計することを避ける。

## 2. 原則

Viewは「責務間のしがらみを一手に引き受ける、なんでも知っている仲介人」である。
ただしView自身は業務判断を行わない。

- 正本／ドメイン責務: 業務事実を記録し、業務判断を確定する。
- View更新: 確定済み情報を収集し、参照しやすい形へ整形し、Viewへ記録する。
- View: 高速参照用の情報を保持する。
- 表示／Query: 原則Viewを読み、同じ情報を得るため正本を再横断しない。

```text
05 請求 ─────┐
06 入金 ─────┤
07 出席 ─────┼─→ View更新 ─→ View / TB ─→ Query / 表示
09 Evidence ─┘
```

## 3. View更新の責務

View更新処理は次の三段階に限定する。

`Collect → Shape → Record`

Collectは正本を読む。Shapeは名称変換、合計、件数、一覧化などRead Model生成に必要な機械的整形を行う。RecordはViewへupsertする。

料金プランの決定、出席を課金対象とするか、支払いを成立させるか等の業務判断をViewへ持ち込まない。

## 4. TB端子

表示側が必要とする情報は、表示時に探索・再集計せずに済むようViewの端子として用意する。
不足端子を理由に表示側から正本へ迂回配線を追加しない。必要な端子をViewへ追加する。

同時に、粒度の異なる情報を一つのViewへ無理に混在させない。必要なら粒度ごとにRead Modelを分ける。

## 5. 更新入口

同一Viewの生成・更新入口は一本化する。
20_会費状態Viewは `paymentStatusView_refresh()` を正規更新入口とする。
呼出元はView行を自力で生成・直接更新しない。

## 6. 参照時ルール

Query／表示は原則Viewのみを読む。
Viewに行が存在しない場合のlazy refreshは移行期間の安全網として許容するが、通常運用では正本更新時にViewも更新されている状態を目標とする。

## 7. 検証

Runnerは実際の業務処理を実行し、その結果としてViewの全端子が正しく更新されることを確認する。
Checkerは既存の正本とViewを読み、両者の整合性を検査する。

画面表示の正否をView生成の検証手段にしない。

## 8. 移行ルール

既存コードを次の基準で整理する。

- 業務処理内の独自View生成 → 正規refreshへ置換。
- 表示／Query内の正本横断集計 → View端子へ置換。
- View内の業務判断 → 所有するドメイン責務へ移動。
- 旧View生成入口・重複集計 → 利用箇所を移行後に削除。
