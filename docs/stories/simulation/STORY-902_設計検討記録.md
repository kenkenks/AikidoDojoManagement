# STORY-902 設計検討記録

**対象：2027年7月・一か月試験運用シミュレーション**
**検討日：2026年10月22日**
**状態：スケジュール検討済み／実装仕様の詳細化待ち**

## 1. 目的

STORY-902は、道場システムの一か月分の運用を仮想的に再現し、実際の画面操作に相当するリクエストをWebConnect経由で実行するシミュレーターとする。

単なる業務関数の単体テストではなく、出席登録、会費受付、取消、重複操作、月末集計など、一連の業務が正しく成立することを検証する。

## 2. イベントスケジュールの基本方針【確定】

* 対象期間は2027年7月。
* イベントは原則として、利用者のボタン操作またはシステムイベントを単位とする。
* イベントNoは固定識別子とし、途中にイベントを追加しても既存Noを変更しない。
* イベントNoには業務上の意味を持たせない。
* シミュレーターは仮想日時を進めながらイベントを順番に実行する。
* 業務処理は原則としてWebConnect経由で実行する。
* シミュレーター内に会費計算などの業務ロジックを重複実装しない。
* 未実装の操作もスケジュールから削除せず、システム側の課題として検出する。

## 4. イベント定義に必要な情報【確定】

各イベントには、少なくとも次の情報を持たせる。

| 分類  | 情報                               |
| --- | -------------------------------- |
| 識別  | Story ID、Event ID                |
| 時間  | 仮想日時                             |
| 操作者 | 利用者・役割・権限                        |
| 操作  | 対象画面、ボタン、操作内容                    |
| 入力  | 画面に入力・選択する値                      |
| 通信  | WebConnect action、method、payload |
| 参照  | 対象会員、請求、出席、入金、参照イベント             |
| 応答  | 期待する成功・拒否・エラー                    |
| 状態  | 実行前と実行後の期待状態                     |
| 検証  | 判定条件、実際の応答、PASS/FAIL             |

画面入力値とWebConnectへの送信値は区別する。

期待結果は、単に「成功」とせず、可能な限り請求金額・入金金額・出席件数・関連レコードの状態まで定義する。

## 5. テストデータ管理【確定】

基本方針は、**専用データ＋実行トレーサー**とする。

### 5.1 原則

1. 既存の業務データと衝突させない。
2. シミュレーション専用データを使用する。
3. 実行ごとにRun IDを発行する。
4. 各イベントと生成・更新された業務レコードの対応を追跡する。
5. 実行結果の検証後、シミュレーション用業務データを消去する。
6. 実行ログと検証結果は保存する。
7. 通常データを削除対象に含めない。
8. 本番環境での実行・削除を禁止する。

### 5.2 識別子

| 識別子      | 用途            |
| -------- | ------------- |
| Story ID | シナリオの識別       |
| Run ID   | 実行単位の識別       |
| Event ID | イベントの識別       |
| テスト会員ID  | 通常会員との区別      |
| 業務レコードID | 出席・請求・入金などの追跡 |

会員IDに接頭辞を付ける方式は候補とするが、既存のID制約を確認してから決定する。

Run IDを既存DTOに直接追加するか、シミュレーター側の対応台帳で管理するかも、現行実装の調査後に決定する。

### 5.3 実行手順

```text
実行環境の安全確認
    ↓
Run ID発行
    ↓
専用データの残存確認
    ↓
初期状態の作成
    ↓
イベント順次実行
    ↓
イベント別の結果記録
    ↓
月末最終状態の検証
    ↓
実行結果・トレースの保存
    ↓
専用業務データの消去
    ↓
残存データの確認
```

途中で異常終了した場合も、残存データを検出できる仕組みを設ける。

削除対象が安全に識別できない場合は、自動削除を停止する。

## 7. 必要な管理資料【確定】

STORY-902では、以下を管理する。

**① 初期状態定義**

シミュレーション開始時点の会員・料金プラン・請求・入金・出席など。

**② イベントスケジュール**

仮想日時、操作、入力、WebConnect送信情報、期待結果。

**③ 最終状態定義**

月末の請求・入金・出席・未収金などの期待状態。

**④ 実行トレース**

Run ID、Event ID、送信情報、応答、生成レコード、判定結果。

設計資料と実行結果は区別して保存する。

## 8. 実装方針【確定】

* 既存の内部業務関数を直接呼ぶ旧方式とは区別する。
* 新902はイベント駆動方式とする。
* イベント定義と実行エンジンを分離する。
* 将来、他のSTORYでも共通エンジンを利用できる構成を目指す。
* ただし、現時点で不要な共通化や業務機能の追加は行わない。
* 新902の検証が完了するまで旧902を削除しない。
